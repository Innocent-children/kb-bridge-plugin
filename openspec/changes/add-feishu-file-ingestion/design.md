## Context

飞书文件消息与文字命令分离。OpenClaw 会把文件下载到本地媒体目录，并在完整入站上下文中暴露 `MediaPath(s)`，但现有插件只处理文字和 URL 型附件。插件必须在文件仍可访问时判断入库意图、读取文件并交给 Knowledge Bridge，同时不得干扰普通文件消息。

## Goals / Non-Goals

**Goals:**

- 提供确定的“入库文件”指令后接单文件流程。
- 以发送人和会话隔离短时意图，避免群聊串单。
- 将文件字节安全传输给 Knowledge Bridge，并复用现有任务状态通知。
- 避免媒体占位文本进入文字候选入库。

**Non-Goals:**

- 不在插件内解析 PDF、Office 文档或生成知识切片。
- 首版不支持多文件批次、跨进程意图恢复或文件先发后确认。
- 不修改 OpenClaw 飞书渠道的群聊提及过滤逻辑。

## Decisions

1. 使用命令先行的两段式交互。插件以 `accountId + sessionKey + senderId` 为 key 保存 2 分钟意图；重复命令刷新意图，取消命令清除意图。相比收到所有文件后再询问，这不会暂存普通文件或猜测用户意图。
2. 在 `reply_dispatch` 处理文件。该 hook 能取得完整媒体上下文并 claim 当前消息；现有文字 hook 继续服务文字入库。插件兼容下限提升至 OpenClaw 2026.4.5。
3. 意图只由同 key 的下一条有效单文件消息原子消费。无意图、过期、其他用户或其他会话的文件不 claim。无媒体路径但存在媒体占位符时返回下载失败。
4. 文件使用 multipart 流式上传。插件只读取 OpenClaw 媒体根目录内的普通文件，不把本地路径作为 URL 传递。稳定 requestId 为账号、会话、发送人、消息 ID 和媒体序号的 SHA-256。
5. 上传成功后复用现有 taskId 轮询。首次响应报告“已接收”，终态报告完成、失败或轮询超时。
6. 自动候选入口统一排除媒体占位消息，文件入库仅由显式意图路径触发。

## Risks / Trade-offs

- [群聊 `requireMention=true` 可能在 hook 前丢弃纯文件] → 首版要求目标群关闭该过滤或使用私聊，并在文档中明确部署条件。
- [OpenClaw 媒体上下文字段变化] → 增加针对支持版本的 hook 契约测试并保守校验字段。
- [插件进程在两条消息之间重启] → 首版意图失效，用户重新发送命令；持久化意图延期。
- [上传失败后意图状态不确定] → 进入 SUBMITTING 后使用稳定 requestId；失败时给出重试指令，不自动重复创建。

## Migration Plan

1. 先部署 KBVector 和 Knowledge Bridge 新契约。
2. 再部署插件并提升 OpenClaw 兼容下限。
3. 为目标飞书群确认提及过滤配置；回滚插件即可停止新文件入口，已提交任务继续由后端完成。

## Open Questions

无。首版格式和大小由 Knowledge Bridge 配置决定，插件只执行基础单文件校验。
